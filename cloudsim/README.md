# CloudSim Provisioning Simulation

This directory contains the Java-based CloudSim evaluation module (`ProvisioningSimulation.java`), which bridges the machine learning workload predictions from the MTTD framework into cloud resource provisioning simulations.

---

## 1. Purpose

The simulation evaluates how workload prediction accuracy translates into actual cloud infrastructure metrics:
- Virtual Machine (VM) provisioning efficiency
- SLA violations caused by under-provisioning
- Resource waste caused by over-provisioning
- Response latency / makespan for request processing

It models a cloud data center receiving hourly traffic loads based on the predictions generated by `mttd_bridge.py`.

---

## 2. Required Libraries

To compile and run `ProvisioningSimulation.java`, two JAR libraries are required:

1. **CloudSim 3.0.3**:
   Download the binary distribution from the official release:
   [CloudSim 3.0.3 Release](https://github.com/Cloudslab/cloudsim/releases/tag/cloudsim-3.0.3)
   Required jar: `cloudsim-3.0.3.jar`

2. **Apache Commons Math 3**:
   Required dependency for CloudSim statistical distributions:
   `commons-math3-3.6.1.jar`

> **Note:** These JAR files are external dependencies and are not bundled in this git repository.

---

## 3. Compilation and Execution

The class belongs to the `mttd` package.

### Step 1: Prepare Input Files

Ensure that the prediction files are present in the directory from which the Java process is launched (or update the file path constants in `ProvisioningSimulation.java`):
- `predictions_retrain.csv` (generated by `python mttd_bridge.py --csv data/cricket_hourly_workload.csv --out results/predictions_retrain.csv`)
- `predictions_noretrain.csv` (generated by `python mttd_bridge.py --csv data/cricket_hourly_workload.csv --out results/predictions_noretrain.csv --no-retrain`)

### Step 2: Compile

Assuming dependencies are placed in a `jars/` directory at the repository root:

```bash
# Windows PowerShell
javac -cp "jars/cloudsim-3.0.3.jar;jars/commons-math3-3.6.1.jar" -d bin cloudsim/ProvisioningSimulation.java

# Linux / macOS
javac -cp "jars/cloudsim-3.0.3.jar:jars/commons-math3-3.6.1.jar" -d bin cloudsim/ProvisioningSimulation.java
```

### Step 3: Run

```bash
# Windows PowerShell
java -cp "bin;jars/cloudsim-3.0.3.jar;jars/commons-math3-3.6.1.jar" mttd.ProvisioningSimulation

# Linux / macOS
java -cp "bin:jars/cloudsim-3.0.3.jar:jars/commons-math3-3.6.1.jar" mttd.ProvisioningSimulation
```

## 4. Evaluated Provisioning Policies

For each simulated hour, the datacenter provisions VMs according to five distinct policies:

1. **`REACTIVE` (Threshold Baseline):**
   Provisions VMs based on the **previous hour's observed load** ($t-1$). This represents conventional reactive autoscalers that scale only after observing traffic shifts.
2. **`MTTD-noRetrain`:**
   Provisions VMs using forecasts from the candidate model selected at initialization, without subsequent adaptive retraining (`predictions_noretrain.csv`).
3. **`MTTD-Retrain` (Full MTTD):**
   Provisions VMs using forecasts from the active model in the adaptive MTTD framework with two-strike retraining (`predictions_retrain.csv`).
4. **`ORACLE` (Upper Bound):**
   Provisions VMs using the **exact actual load** of the current hour ($t$). Represents the theoretical optimum with perfect foresight.
5. **`MTTD-Hybrid`:**
   Provisions VMs using $\max(\hat{y}_t, y_{t-1})$. Combines MTTD proactive predictions with the reactive floor to prevent under-provisioning during unexpected flash-crowd bursts.

---

## 5. Metrics Definitions

| Metric | Definition | Impact |
|---|---|---|
| **VM-Hours** | $\sum_{t=1}^{N} \text{Allocated VMs}_t$ | Total computing resource consumption |
| **Wasted VM-Hours** | $\sum_{t=1}^{N} \max(0, \text{Allocated VMs}_t - \text{Required VMs}_t)$ | Economic cost of over-provisioning |
| **SLA Violations** | Count of hours where cloudlet makespan exceeded 3,600 seconds | Quality-of-service degradation |
| **Under-provisioned Hours** | Count of hours where $\text{Allocated VMs}_t < \text{Required VMs}_t$ | Capacity deficit indicating imminent SLA risk |
| **Average Makespan** | Mean completion time of all cloudlets across all simulated hours | Service latency |

## 6. Simulation Configuration and `MAX_HOURS`

- **`MAX_HOURS = 0` (Full Run):**
  Simulates every hour present in the prediction CSVs (all 1,080 hours of the deployment phase).
  All reported numbers in research papers and benchmark reports must be generated with `MAX_HOURS = 0`.
- **`MAX_HOURS > 0` (Test Run):**
  Limits simulation to the first $N$ hours for quick debugging and verification.

## 8. Known Simplifications

1. **Hourly Granularity:** Allocation decisions occur strictly on discrete 1-hour boundaries; dynamic sub-hour VM spin-up/spin-down delays are not modelled.
2. **Homogeneous Infrastructure:** All VMs are identical single-core instances (1,000 MIPS, 4,000 hits/hour capacity).
3. **Headroom Buffer:** A fixed 10% headroom (`HEADROOM = 1.10`) is applied to proactive policies to accommodate intra-hour burstiness.
